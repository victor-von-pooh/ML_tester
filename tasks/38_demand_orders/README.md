# 38 時間をまたぐ量の判断を問題の設定から推論まで通す (発注の数)

## 目的

時間をまたぐ量の判断の課題 (商品ごとの日ごとの売れた数の記録から, 先の期間の需要を分位点で予測し, 品切れの損と売れ残りの損の比から決まる分位点で, 商品ごとに発注の数を決める) を, 問題の設定から推論まで, 5 つの画面のアプリ (ML-Pathfinder, ML-Fathom, ML-CreateArchitecture, ML-Dashboard, ML-Provide) の API だけで, 画面と同じ順に通す. 段階ごとに, 画面だけでできたか (OK), 値や場所を手で写すか打つか (手), 誤りかを表にする.

- **課題**: ML-Pathfinder の見本「解約の引き止め」から作り, 課題, 指標, 決めること, 受け持ちを発注の課題に答え直す (架空). 今のやり方は前の 7 日と同じ数を発注する. 1 商品の発注の数の上限は 150
- **受け持ち**: 予測するで, 出す値は分布, 正解の種類は先の期間の需要. 商品の id の列 `product_id`, 日付の列 `date`, 売れた数の列 `units`, 在庫の数の列 `stock`, 行の id の列 `record_id`, 予測に使う列 `category`, 先の期間 7 日, 学ぶ水準は既定 (0.1, 0.25, 0.5, 0.75, 0.9), 最良を選ぶ指標は分位点の損失, 判断は発注 (品切れの損 3, 売れ残りの損 1, 発注の数の上限 150. 水準 τ = 3 / (3 + 1) = 0.75)
- アプリの起動と段階の記録は 25 の `apps.py` を使う

## ディレクトリ構成

```
38_demand_orders/
├── journey.py   # 合成の記録を作り, 問題の設定から推論まで通す (部品は 25 の apps.py)
└── README.md
```

作業用の場所 (既定は一時ディレクトリ. `--work` で変えられる) に置くものは 25 と同じ.

## データ

`journey.py` が作業用の場所に作る合成の日ごとの記録 (12 商品 × 240 日 = 2,880 行. 乱数を固定). 列は `record_id`, `product_id`, `date`, `category` (0 か 1), `units` (その日に売れた数), `stock` (その日の在庫の数. 0 から 9 の一様), `waste` (廃棄の数. 売れた後に決まる列で, 予測に使わない). 売れた数は平均が「商品の水準 (2 + 商品の番号を 6 で割った余り + 種類 1 なら 4) × 週末なら 1.8 × 学習の記録の 240 日で 1 から 1.3 へ上がる傾き」のポアソン分布. 推論には, 同じ作り方で別の乱数の種から作った 60 日の記録 (`daily_trial.csv`. 720 行. 傾きは 1 から 1.075 まで) を使い, 商品ごとの最後の日 (発注を決める日) の売れた数を空にする. 学習に使った行で発注の数を決めないため. 用意してもらうデータは無い.

## モデル

ML-CreateArchitecture の需要の雛形 `tabular_demand` を, データセットの列の数と学ぶ水準の数に書き換えたもの (出力は先の期間の需要の分位点を水準の小さい順に並べた `quantiles`). 雛形は問題の設定から決まり (`POST /api/project/target` の `example`), 列の数と水準の数は `POST /api/dataset/inputs` (データセットの入力と, 問題の設定の学ぶ水準) から `POST /api/templates/adapt` で書き換える (画面の「データセットから入力と出力を作る」と同じ値).

## 学習の設計

ML-Pathfinder が書き出した骨組み (`train.py`) を書き換えずに, ML-Dashboard の「学習を起動」で動かす. 骨組みは時間の順に分け, 学習の前に初めの分位点を学習用の需要の平均に合わせ, 既定の 100 エポック (検証用の損失が 10 エポック続けて良くならなければ止める) のうち検証用の分位点の損失 (`valid/loss`) が最も小さいエポックを選び, 検証用とテスト用の需要の評価 (`evaluations/demand_<分割>.json`. 0.5 の分位点の平均絶対誤差 `mae`, 分位点の損失 `pinball_loss`, 水準 τ の分位点から在庫を引いた発注の数での損 `order_cost` と, 前の期間と同じ数を発注したときの損 `baseline_cost` とその差と比) を書き, 需要の推論の一式を実験の `inference/` に作る (版 14).

## 実行方法

25 の README の「実行方法」と同じく, 5 つのアプリをこのリポジトリと同じディレクトリに clone して `make setup` を済ませ, ルートのディレクトリで実行する (`uv` が要る). 手元で動かせなければ, CI の「通しを測る」(`.github/workflows/journeys.yml`) を `tasks` に `38_demand_orders` を入れて手で起動する.

```bash
.venv/bin/python tasks/38_demand_orders/journey.py               # 1 分ほど (環境づくりはネットワークを使う)
.venv/bin/python tasks/38_demand_orders/journey.py --work <作業用の場所> --apps <アプリの親のディレクトリ>
```

- 最後に段階ごとの表と, 手の段階と誤りの段階の数を出す. 誤りがあれば終了の番号は 1
- 学習の環境はプロジェクトの `.venv` に, ML-Found と ML-EDA, ML-ModelControl, ML-Inference を git から入れる (uv の手元のキャッシュがあれば十数秒)

## 気付いたこと

- **雛形のモデルも初めの分位点を需要の平均に合わせる**: ML-Quest の時間をまたぐ量の判断の骨組みは, 売れた数の目的を尺度を変えずに学ぶ. ML-CreateArchitecture で保存した雛形 `tabular_demand` の定義から組んだモデルでも, 学習の前に初めの分位点を学習用の需要の平均に合わせるので, 既定の 100 エポックで分位点の損失が下がりきり (ベストはエポック 97), 発注の損が前の期間と同じ数の発注より小さくなる
- ML-Fathom の書き出しの「出す値」は 1 (水準 1 つあたりの値) で, 学ぶ水準の数は問題の設定 (と学習の設定) が決める. ML-CreateArchitecture の `POST /api/dataset/inputs` は問題の設定を渡すと学ぶ水準を返し (`demand.levels`. 骨組みを書き出した後は学習の設定から), 雛形の水準の数はそこから書き換える
- ML-CreateArchitecture の `POST /api/dataset/inputs` は, 時間をまたぐ量の判断の商品, 日付, 売れた数, 在庫の数の列を ML-Fathom が parquet で書き出した表から読む. 追加の依存 `project` の ML-EDA に pyarrow があるので表まで読め, 保存の注意も出ない
- 需要の一式は ML-Provide で問題の設定を使わない (発注の判断は ML-Quest が骨組みの config に写し, 骨組みが一式に写す). 学習の後に損や上限を変えるには, 推論で発注の判断 (`decision`) を渡すか, 問題の設定を直して骨組みを書き出し直す
- 時間をまたぐ量の判断には見本が無いので, 見本「解約の引き止め」から作って課題と受け持ちを答え直す (ML-Pathfinder の時間をまたぐ量の判断のテストと同じ作り方). 推論の表は商品ごとの履歴の最後の日 (売れた数が空) で発注の数を決め, それより前の行はずらしの特徴にだけ使う (読んだ 720 行のうち推論は 12 行)
