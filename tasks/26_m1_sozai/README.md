# 26 時系列の予測を画面の API だけで通す (総菜の作る量)

## 目的

節目「表の予測を画面だけで通す」(ROADMAP.md の 4 の節の「済んだこと」) の確かめのうち, 時系列の予測と k 期前の今のやり方. 25 と同じく, 問題の設定から推論までを 5 つの画面のアプリの API だけで, 画面と同じ順に通し, 段階ごとに OK, 手, 誤りを表にする. アプリの起動と段階の進め方は 25 の `apps.py` を使う.

- **課題**: ML-Pathfinder の見本「総菜の作る量」(架空). 前の日の 17 時に, 店と品ごとの翌日の作る量を決める. 1 個足りないと粗利 200 円, 1 個余ると原価 150 円の損
- **今のやり方**: 前の週の同じ曜日と同じ数を作る. 問題の設定の「今のやり方をデータで書くと」に k 期前 (`lag`, 7 期) で答える. 列は無く, 骨組みの評価と ML-Provide のたどり直しが, 同じ決まりから行ごとの値を作る
- **前処理**: ML-Fathom の雛形 (除く列, 系列ごとの 2 日前の売れた数) に, 7 日前と, 2 つ前から始める 7 日の移動平均, 欠損の行を落とす, 曜日と月, 店と品のワンホット, 標準化を足す

## ディレクトリ構成

```
26_m1_sozai/
├── journey.py   # 合成のデータを作り, 時系列の予測で通す (部品は 25 の apps.py)
└── README.md
```

作業用の場所の中身は 25 と同じ.

## データ

`journey.py` が作業用の場所に作る合成の 2 店 × 3 品の 365 日の売れた数 (2,190 行. 乱数を固定). 列は `date`, `store`, `item`, `sales` (目的の列), `temperature_forecast`, `promo`, `customers` (予測の時点では分からない列. 問題の設定の見本で除く). 品の水準, 週末, 特売, 気温 (サラダは暑いほど, 他は寒いほど売れる) で決まる. 推論とたどり直しには, 最後の 90 日 (`sozai_past.csv`. 540 行) を使う. 用意してもらうデータは無い.

## モデル

25 と同じ (入力 `x` の形は学習に使う列の数 12, 全結合の `head` の出す値 1).

## 学習の設計

25 と同じ. 骨組みの `train.py` を書き換えずに, ML-Dashboard の画面から作った環境で学習する. 監視する指標は問題の設定の平均絶対誤差 (`valid/mae`). 段階と API も 25 と同じで, 学習の後に直す損得は 1 個足りない損 (200 から 300 に).

## 確かめること

- [x] k 期前の今のやり方から, 問題の設定がデータの上の今のやり方の損を出す
- [x] ML-Fathom の雛形が, 決める時点で分かる 2 日前からの過去の値の手順で始まる
- [x] 移動平均をいくつ前から始めるか (`gap`) を使ったレシピの一式を, ML-Provide で推論できる
- [x] 骨組みが k 期前の今のやり方の評価を書き, ML-Dashboard の結果に出る
- [x] ML-Provide で一式に問題の設定をつなぐと, 今のやり方の決まり (k 期前, 時刻の列, 系列を分ける列, 間隔) が入り, 推論するデータに列を足さずにたどり直せる
- [x] 学習の後に ML-Pathfinder で足りない損を直すと, ML-Provide の次の推論の既定と推論で使う値に入る

## 期待する結果

誤りの段階 0, 手の段階 0. 骨組みの評価で, モデルの平均絶対誤差が今のやり方より小さい.

## 実行方法

準備は 25 と同じ. ルートのディレクトリで実行する.

```bash
.venv/bin/python tasks/26_m1_sozai/journey.py               # 2 分ほど
```

`--apps` と `--work` も 25 と同じ.
