# 30 文の分類を画面の API だけで通す (問い合わせの文)

## 目的

節目「画像と文の分類を画面で通す」(ROADMAP.md の M3) の確かめ. 文の分類を, 問題の設定から推論まで 5 つの画面のアプリの API だけで, 画面と同じ順に通す. 段階ごとに, 画面だけでできたか (OK), 値や場所を手で写すか打つか (手), 誤りかを表にする.

- **課題**: ML-Pathfinder の見本「解約の引き止め」(架空) の問いの答えを, 文の表 (ML-EDA の `load_data` の列) に合わせたもの. 当たりのクラスは `complaint` (苦情)
- 通しは 29 と同じく 25 の `apps.py` の `run_journey` をそのまま使い, 中身の手順 (分析が勧める区切り方) とモデルの作り方だけを設定の関数で渡す
- 画像の分類は 29 で確かめる

## ディレクトリ構成

```
30_m3_text_classes/
├── journey.py   # 合成の文を作り, 文の分類で通す (29 の classes.py を使う)
└── README.md
```

作業用の場所に置くものは 25 と同じ.

## データ

`journey.py` が作業用の場所に作る合成の日本語の問い合わせの文. `<クラス>/<文>.txt` のディレクトリで, クラスは `complaint` (苦情) と `question` (質問) (各 80 件). 文は「いつから」の部品, クラスを決める中身, 結びの組み合わせで, 同じ文は作らない. 推論とたどり直しには, 別の乱数の種から学習の文と重ならないように作った各 10 件 (`inquiries_past`) を使う. 用意してもらうデータは無い.

クラスを 2 つにするのは, 29 と同じく見本の意思決定 (対象を選ぶ) が 2 クラスの分類の一式にだけ使えるため.

## モデル

ML-CreateArchitecture の同梱の例 `lstm_classifier` (入力 `ids` [4, 12] int64, 埋め込み `emb` の `num_embeddings` 100, LSTM, 最後の隠れ状態, 全結合の `head` の出す値 2). 29 の `classes.py` の `apply_dataset_inputs` で, 画面の「データセットから入力と出力を作る」と同じく入力と出力を当てる. 画面は埋め込みの語彙の数を当てないので, 利用者が ML-Fathom の書き出しの結果 (`hints` の `vocabulary`. データセットの `recipe.yaml` の `vocabulary` の手順の語彙の長さと同じ値) を `num_embeddings` に写す. これを「手」と数える.

## 学習の設計

骨組みの `train.py` を書き換えずに, ML-Dashboard の「学習を起動」で動かす. 段階と API は 25 の README の「学習の設計」と同じで, 29 の README の「学習の設計」の段階のうち, 中身の手順を次に変える.

| 段階 | アプリ | API |
| --- | --- | --- |
| 分析の結果の区切り方の勧め (`items` の `tokenizers` の `recommended`) を中身の手順にする (画面で勧めを選ぶのと同じ値) | ML-Fathom | `GET /api/sources/{id}/profile` |
| 同梱の例を開き, 入力と出力を当て, 埋め込みの語彙の数を手で写し, 形を確かめる | ML-CreateArchitecture | `GET /api/examples/lstm_classifier`, `GET /api/units`, `POST /api/check` |

## 実行方法

29 と同じ. CI の「通しを測る」では `tasks` に `30_m3_text_classes` を入れる.

```bash
.venv/bin/python tasks/30_m3_text_classes/journey.py
.venv/bin/python tasks/30_m3_text_classes/journey.py --work <作業用の場所> --apps <アプリの親のディレクトリ>
```

## 気付いたこと

- 手の 1 つは埋め込みの語彙の数. ML-Fathom はプロジェクトへの書き出しの結果に語彙の大きさ (`hints` の `vocabulary`) を返すが, ML-CreateArchitecture の「データセットから入力と出力を作る」(ML-EDA の `model_inputs`) は語彙の大きさを返さず, 画面も埋め込みに当てない. 写さないと, 例の 100 のままで, 語彙の 320 より小さい番号の範囲になる
- 誤りの 2 つは 29 と同じく, 文のディレクトリの表 (`text`, `file`, `label`, `length`, `words`) に今のやり方の列が無く, 対象を選ぶ意思決定の今のやり方 (ML-Quest の `action.current`) を書けないため
- 分析が勧めた部分語の区切り (ML-EDA の README の「画像, 文, 点群」) をそのまま使うと, 学習の環境 (骨組みの `requires` の `eda`) には部分語のライブラリ (`tokenizers`) が入らないが, 書き出したデータセットは番号の配列なので学習と推論の一式の作成は通る. ML-Provide の推論も新しい文を同じ区切りで番号にして通る
- 同梱の例の入力は値の作り方が `arange` (0 からの連番) で, 形の確かめは入力の要素の数 (ここでは 4 x 8 = 32) までの番号を埋め込みに渡す. 語彙の数がそれより小さいと, 確かめが番号の範囲の外で失敗する. この通しの語彙 (320) では起きない
