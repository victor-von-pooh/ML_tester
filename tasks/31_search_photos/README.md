# 31 似た写真を探すを問題の設定から推論まで通す (合成の写真)

## 目的

節目「似た写真を探す (並べるで, 既製のモデルをそのまま) を画面で通す」(ROADMAP.md の 4 の節の「済んだこと」) の確かめ. 似た写真を探す課題を, 問題の設定から推論まで, 画面のアプリ (ML-Pathfinder, ML-Provide) の API と, 書き出した骨組みの `bundle.py` で, 画面と同じ順に通す. 段階ごとに, 画面だけでできたか (OK), 値や場所を手で写すか打つか (手), 誤りかを表にする.

- **課題**: ML-Pathfinder の見本「似た商品の写真を探す (既製の埋め込み)」(架空). 客から届いた商品の写真に, 見た目の近い商品の写真を上位 5 件返す. 1 件の問いの待ち時間の上限は 200 ms. 既製のモデルは torchvision の `resnet18` (重み `IMAGENET1K_V1`. 重みの hash を問題の設定に決めておく)
- 学習しないので, データの分析, モデルの作成, 学習の段階 (ML-Fathom, ML-CreateArchitecture, ML-Dashboard) は通らず, 起動もしない. 索引と評価と検索の一式は, 骨組みの `bundle.py` が作る. 画面に無い段階なので, 骨組みの README の「次にすること」のとおりコマンドで動かし, 手と数える
- アプリの起動と段階の記録は 25 の `apps.py` を使う (起動するアプリを ML-Pathfinder と ML-Provide に絞る)

## ディレクトリ構成

```
31_search_photos/
├── journey.py   # 合成の写真を作り, 似た写真を探す課題で通す (部品は 25 の apps.py)
└── README.md
```

作業用の場所 (既定は一時ディレクトリ. `--work` で変えられる) に置くものは 25 と同じ. 加えて, ログ (`logs/`) に一式づくりの環境づくり (`bundle_env.log`) と `bundle.py` の出力 (`bundle.log`) を, 書き出したプロジェクト (`project/`) に一式づくりの環境 (`.venv`), 埋め込みの一式 (`outputs/embedder`), 成果物 (`outputs/search`), 検索の一式 (`outputs/inference`) を置く.

## データ

`journey.py` が作業用の場所に作る合成の写真. `<種類>/<写真>.png` のディレクトリで, 種類は `circle`, `square`, `triangle`, `stripes` (横の縞) の 4 つ (各 20 枚, 計 80 枚. 乱数を固定). 64x64 の RGB で, 色の違う雑音の背景に, 色と位置と大きさの違う図形を 1 つ描く. 色では種類が分からないので, 写真を縮めた画素をそのまま並べる比べる相手では探しにくい. ML-Provide で探す問いの写真には, 同じ作り方で別の乱数の種から作った各 3 枚 (`queries`. 計 12 枚) を使う. 用意してもらうデータは無い.

## モデル

学習しない. 骨組みの config の既製のモデル (torchvision の `resnet18`, 重み `IMAGENET1K_V1`) の分類の最後の層の手前の出力 (幅 512) を写真の埋め込みにする (ML-Inference の既製のモデルの一式). 重みは一式に写さず, 使うときに出どころから読み, 問題の設定の hash で確かめる. 初回は重みを取りに行く (ネットワークを使う).

## 学習の設計

学習しない. 段階と API は次のとおり.

| 段階 | アプリ | API かコマンド |
| --- | --- | --- |
| 見本から問題の設定を作り, 写真のディレクトリを入れる | ML-Pathfinder | `POST /api/problems`, `POST /api/problems/{id}/data` |
| 骨組みを書き出す (写真はプロジェクトの `data` に写り, config の `data.photos` が指す) | ML-Pathfinder | `POST /api/problems/{id}/project` |
| 一式づくりの環境を作る (骨組みの README の入れ方. ML-Inference と `ml-modelcontrol[torchvision]` を git から) | 無し (手) | `uv venv`, `uv pip install` |
| 索引と評価と一式づくり (骨組みを書き換えない) | 無し (手) | `python bundle.py` |
| 一式を場所で登録する | ML-Provide | `POST /api/bundles` |
| 一式の画面の問題の設定の欄を見る (問題の設定を使わない一式 (`uses_problem` が偽) は欄が無く, つながない. 使う一式なら候補を見て元の問題の設定をつなぐ) | ML-Provide | `POST /api/bundles` の `uses_problem`, `GET /api/bundles/{id}/problem`, `PUT /api/bundles/{id}/problem` |
| 問いの写真のディレクトリを推論し, 問いごとの上位 K 件を読む (件数は一式の既定) | ML-Provide | `POST /api/bundles/{id}/predict`, `GET /api/results/{id}/rows` |

`bundle.py` は写真を種類ごとに 2 割ずつ (4 枚) 検証用の問いにし (`data.valid` 0.2), 残りの 64 枚を索引にする. 問いごとに索引の写真を余弦の近さで上位 5 件並べ, 問いと同じ種類の写真を正解にした Recall@K と NDCG@K を, 写真を縮めた画素をそのまま並べた比べる相手と比べる. 推論では, 問いの写真の種類 (読み込みの表の `label`) と並んだ写真の種類から, 1 位が同じ種類の問いの数と, 上位 5 件のうち同じ種類の割合の平均を数える.

## 期待する結果

手の段階 2 (一式づくりの環境と `bundle.py`. 画面に無い段階), 誤りの段階 0. 骨組みの評価で, 埋め込みの Recall@K と NDCG@K が写真を縮めた画素より大きい. Recall@K は, 問いと同じ種類の索引の写真が 16 枚あり上位 5 件しか並べないので, 最大でも 5 / 16 = 0.3125.

## 実行方法

25 の README の「実行方法」と同じく, ML-Pathfinder と ML-Provide を ML_tester と同じディレクトリに clone して `make setup` を済ませ, ルートのディレクトリで実行する (`uv` が要る). 手元で動かせなければ, CI の「通しを測る」(`.github/workflows/journeys.yml`) を `tasks` に `31_search_photos` を入れて手で起動する.

```bash
.venv/bin/python tasks/31_search_photos/journey.py               # 1 分ほど (環境づくりと重みの取得はネットワークを使う)
.venv/bin/python tasks/31_search_photos/journey.py --work <作業用の場所> --apps <アプリの親のディレクトリ>
```

- 最後に段階ごとの表と, 手の段階と誤りの段階の数を出す. 誤りがあれば終了の番号は 1
- 一式づくりの環境はプロジェクトの `.venv` に, ML-Inference と ML-ModelControl を git の main から入れる (uv の手元のキャッシュがあれば数秒)
- 重みは PyTorch の置き場 (`torch.hub.get_dir()` の `checkpoints`) に置かれ, 次からはそれを読む

## 気付いたこと

- 似た写真を探すは, 問題の設定から推論まで, 画面の API と骨組みの `bundle.py` で通る. 段階の間で値や場所を写す所は無い (写真の場所, 返す件数, 待ち時間の上限, 既製のモデルと重みの hash は, 問題の設定から骨組みの config に, config から一式に入る). 手の段階は, 画面に無い一式づくりの環境と `bundle.py` の 2 つ. 骨組みの README の「次にすること」がこの 2 つを書く
- ML-Provide の検索の一式は問題の設定を使わない (返す件数と待ち時間の上限は ML-Quest が骨組みの config に写し, `bundle.py` が一式に写す). 登録の応答の `uses_problem` が偽で, 一式の画面に問題の設定の欄が出ない. 問題の設定を直したら, 骨組みを書き出し直して一式を作り直す (ML-Provide の docs/DESIGN.md の「検索の一式 (一式の版 15)」)
- 一式を作るときに, `bundle.py` が「重みのライセンスは 分からない (unknown) です. 商用で使う前に配布元で確かめてください」と注意を出す. 骨組みの README の 3 のとおり, 使ってよいかは配布元で確かめる
- 検索の一式は ML-Provide の実験の一覧 (ML-Dashboard の実験) に出ないので, 場所で登録する. 一式の場所は骨組みの config の `bundle.path` (`outputs/inference`) で, 骨組みの README の 2 と `bundle.py` の出力にも出る
