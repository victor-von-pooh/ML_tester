# 21 問題の設定から推論まで (5 つの段階の通し)

## 目的

問題の設定の段階 (ML-Quest) から始めて, データの分析 (ML-EDA), モデルの作成 (ML-ModelControl), 学習 (ML-Found), 推論と意思決定 (ML-Inference) までを通しで確かめる. 20 では, 損得の値や比べる相手を作る側の想定で置いた. ここでは, それらを問題の設定のファイル (`problem.yaml`) から取る.

- **課題** (ML-Quest の見本「総菜の作る量」. 架空): 店長の課題は, 総菜の廃棄が多く, 夕方には品切れも出ること. 今のやり方は「前の週の同じ曜日と同じ数を作る」. 解けたと言える指標は廃棄と欠品の損 (小さいほど良い), 成功の基準は「今のやり方より 2 割少ない」
- **機械学習の受け持ち**: 翌日の品ごとの売れる数を予測し (時系列の予測), 前の日の 17 時に作る量を決める. 損得は 1 個足りないと粗利 200 円, 1 個余ると原価 150 円
- **データ**: 合成した 3 店 × 4 品の 540 日の売れた数 (`make_data.py`. 乱数を固定). 品の水準, 店の大きさ, 曜日, 天気予報の気温, 特売, 前の日からの続きで決まる. 当日の客数 (`customers`) は売れた数と一緒に決まり, 予測の時点では分からない列
- **前処理**: 問題の設定の受け渡しの値 (目的の列, タスク, 時刻の順の分割, 時刻の列, 系列を分ける列, 過去の値の列の最も小さいずらし幅, 学習に使ってよい列) から作ったレシピ (`prepare.py`)
- **学習**: ML-Quest が書き出した骨組みの `project/train.py` を書き換えずに使う

## ディレクトリ構成

```
21_problem_setting/
├── make_data.py        # 元のデータ (data/sozai.csv) を作る
├── setup_problem.py    # 問題の設定を確かめ, problem.yaml と骨組み (project/) を書き出す
├── problem.yaml        # 問題の設定 (setup_problem.py が書く)
├── prepare.py          # 受け渡しの値でデータセットとモデルの定義を project/ に置く
├── evaluate.py         # 問題の設定の損得で, 今のやり方とたどり直して比べる
└── project/            # ML-Quest が書き出した ML-Found のプロジェクト (README.md, problem.yaml, configs, train.py) と, prepare.py が置く models/model.yaml
```

## データ

合成した 3 店 × 4 品の 540 日の売れた数 (`make_data.py` が `data/sozai.csv` に 6,480 行を書く. 乱数を固定). 用意してもらう必要があるデータは無い. 前処理のレシピは, `prepare.py` が問題の設定の受け渡しの値から作る (上の「目的」).

## モデル

`prepare.py` が受け渡しの値 (学習に使う列の数) から `project/models/model.yaml` に置く, 全結合の 3 層 (幅 64, ReLU) のモデルの定義 (ML-ModelControl).

## 学習の設計

ML-Quest が書き出した骨組みの `project/train.py` を書き換えずに使う. 骨組みが学習の後に推論の一式を作り, 問題の設定の損得を意思決定の既定値に入れる. 比べる相手 (今のやり方) とのたどり直しは `evaluate.py` が行う.

## 実行方法

ルートのディレクトリで, `.venv` を有効にして実行する (他の場所から実行してもよい).

```bash
python tasks/21_problem_setting/make_data.py        # data/sozai.csv (6,480 行)
python tasks/21_problem_setting/setup_problem.py    # problem.yaml と project/ の骨組み
python tasks/21_problem_setting/prepare.py          # project/outputs/dataset と project/models/model.yaml
python tasks/21_problem_setting/project/train.py    # 学習と推論の一式 (10 秒ほど)
python tasks/21_problem_setting/evaluate.py         # たどり直し
```

- `project/train.py` が「README の『次にすること』」と案内するのは, 骨組みの `project/README.md` のこと (この README の `prepare.py` が, そのうちデータセットとモデルの定義を置く)
- 推論の一式の確かめ (学習の記録と合うか) は, 画面には出ず `project/outputs/<実験>/<日付>/<時刻>/train.log` の最後の行に残る
- `setup_problem.py` は, 答えが前の `problem.yaml` と同じなら時刻を含めて前のものを使う (実行のたびに差分を出さない)

## 結果のメモ

PyTorch 2.15.0, Apple Silicon の Mac (device は auto で MPS) での値.

- 確かめ (`check`) は 0 件. 受け渡しの値は, 目的の列 `sales`, 時系列の予測, 時刻の順の分割, 時刻の列 `date`, 系列を分ける列 `store` と `item`, 過去の値の列の最も小さいずらし幅 2, 学習に使ってよい列 `store`, `item`, `temperature_forecast`, `promo` (とこれらから作る列), 除く列 `customers`, 監視する指標 `valid/mae`
- 学習に使う列は 12 (気温の予報, 特売, 2 日前と 7 日前の売れた数, 曜日, 店と品のワンホット). 骨組みの `train.py` は Early Stopping でエポック 37 で止まり, ベストはエポック 27 の検証用の平均絶対誤差 9.33 個. 推論の一式の確かめは記録と合う
- テスト用の期間 (2026-04-06 から 2026-06-24 の 80 日, 960 行) を, 問題の設定の損得 (足りない 200 円, 余る 150 円) でたどり直した

| やり方 | 実際の損 (円) | 30 日あたり (円) |
| --- | --- | --- |
| この方針 (損の比で決めた量) | 1,705,400 | 639,525 |
| 予測の値どおりに置く | 1,738,600 | 651,975 |
| 今のやり方 (前の週の同じ曜日と同じ数) | 2,777,600 | 1,041,600 |

- この方針は今のやり方より損が 1,072,200 円 (38.6 %) 少ない (日ごとに選び直した 90 % の幅 931,895 から 1,215,868 円). 予測の値どおりに置くよりも 33,200 円少ない (幅 9,942 から 57,507 円). 損の比 (200 : 150) が対称に近いので, 損の比で決めることの上乗せは小さく, 改善の大半は予測そのもの (今のやり方との差 1,072,200 円のうち, 予測の値どおりに置くとの差 33,200 円, 3.1 % が損の比で決めた分)
- **成功の基準について**: たどり直し (80 日) の上では成功の基準 (2 割少ない) を満たした. 問題の設定の確かめ方は「過去 3 か月のたどり直し」と「1 店で 4 週間の試行」の両方で, 試行はしていない
- **確かめの範囲**: データは作り方の分かる合成のデータで, 課題と損得の値も見本の架空のもの. 問題の設定から推論までの値の受け渡しが通ることと, 問題の設定に書いた比べる相手と成功の基準でそのまま評価できることの確かめで, 実際の場面で効く根拠ではない

### 決める時点で分かる過去の値だけを使う

問題の設定は「前の日の 17 時に作る量を決める」なので, 前の日の売れた数 (`sales_lag1`) は決める時点ではまだ確定しない. 学習とたどり直しでだけ当たる値で, 実際に使うと外れる. ML-Quest の問い「決める時点 (4 の「いつ決めますか」) で, 目的の値は何期前の分まで分かっていますか」(`ml.available_lag`) の答えが受け渡しの値 `min_lag` (ここでは 2) になり, `prepare.py` はその値で過去の値の列 (2 日前と 7 日前) を作る.

## 気付いたこと

- 問題の設定を先に決めると, 後ろの段階で想像で埋める値が減る. 損得, 比べる相手, 成功の基準, 使ってよい列, 過去の値の列の最も小さいずらし幅, 監視する指標は問題の設定から取れた. 一方で, 過去の値の幅 (7 日前), 検証用とテスト用の割合 (0.15), モデルの幅 (64) は作り手が決めた (データの分析とモデルの作成の段階で決めること)
- 予測の時点で分かる列だけでなく, 目的の値そのものが何期前まで分かるかも問題の設定で決めること. 問わないと, 過去の値の列で漏れが起きる
- 系列を分ける列が 2 つ (店と品) あると, ML-EDA は読み込みで日時の列を推定できない. 問題の設定の時刻の列を読み込みで指定する (骨組みの README にも書いてある)
- 骨組みの `train.py` は, 比べる相手の評価が印 (TODO) のまま. 比べる相手の作り方 (前の週の同じ曜日) はデータによって違うので, 今は利用者が書く (ここでは `evaluate.py`)
