# 19 学習したモデルで推論し, 結論を出す (推論の段階)

## 目的

推論の段階 (ML-Inference, ML-Provide) で, 17 と 18 で学習したモデルから推論の一式を作り, 新しいデータを推論して結論を出せることを確かめる. 学習のときと同じ前処理とモデルが再現できているかを, 学習のスクリプトが記録したテスト用の評価と同じ値になるかで確かめる.

- **17 (文の分類)**: 言い方を増やした 48,000 件で学習した部分語の BERT (`natural_subword_scratch_48k`). 学習のスクリプトが前処理の外で並びの先頭に [CLS] (語彙の数 + 1) を足しているので, 一式に `prepend` として書く
- **18 (売上の予測)**: 店ごとの売上の全結合のモデル (`store_sales`). 学習のスクリプトが売上を学習用の平均と標準偏差で変えて学習しているので, 一式に `target_scale` として書く. 汚れた元のデータ (表記のゆれ, 重複, 3 つの書き方の日付) をそのまま推論する

学習はしない. このタスクは ML-Found のプロジェクトではなく, 推論のスクリプト `infer.py` だけを持つ.

## 実行方法

ルートのディレクトリで, `.venv` を有効にして実行する (データと出力の場所はスクリプトの場所から決まるので, 他の場所から実行してもよい). 先に 17 の README の 19 から 21 (言い方を増やした 48,000 件のデータ, 部分語での書き出し, BERT の学習) と, 18 の README の 1 から 3 を実行しておく.

```bash
python tasks/19_inference/infer.py
```

CPU で 15 秒ほど (ラベルの無い 100,000 件の推論を含む). 書き出し先は `--out` で変えられる (タスクのディレクトリからの相対パスか絶対パス. 既定の `outputs` は git の管理外). 作った一式 (`outputs/bundle_reviews`, `outputs/bundle_sales`) は, ML-Provide の「場所で登録」で画面から使える.

### 何段も先の予測と列の効き (ML-Inference #7, #8, #10)

18 の一式で, テスト用の期間の始め (2025-09-13) より前を過去の行とし, その後の 7 日 (12 店, 81 行. 先の行は店の表記をそろえ, 重複を除いた. 系列は渡した値で分けるため) の売上を空にして `forecast` に渡した. 予測した売上を次の日の過去の値 (前の行, 7 つ前の行, 7 つの平均) に使いながら, 店ごとに 1 行ずつ進める. 比べるために, 同じ行を実際の過去の売上で 1 つ先だけ予測した (`predict`).

| 2 | 12 | 56,190 円 (7.8 %) | 48,722 円 (6.5 %) |
| 3 | 12 | 69,845 円 (11.1 %) | 60,851 円 (8.9 %) |
| 4 | 12 | 64,378 円 (11.2 %) | 44,413 円 (7.5 %) |

| 6 | 12 | 41,735 円 (6.8 %) | 27,730 円 (4.8 %) |

(平均絶対誤差と, 括弧は平均の割合の誤差)

- 段は店ごとの先の行の順. 休みの日は行が無いので, 7 日のうちに休みのある店 (千葉店, 大宮店, 立川店) は 6 段までで, 段の数と先の日の数がずれる
- 1 段目は 1 つ先の予測と同じ. 2 段目からは, 同じ行の 1 つ先の予測より 0.6 から 3.7 ポイント大きい (前の日の売上が予測の値になるため). 全ての行では 9.6 % と 8.0 %. 7 段目が大きいのは, 1 つ先でも 12.5 % の難しい行だから
- テスト用の期間と前の 30 日の列の効き (`explain`. 並べ替えたときの予測の売上の変わり方): sales (過去の値) 124,437 円, store 120,285 円, date 99,940 円, promo 32,201 円, temperature 30,024 円. 店は系列の名前を入れ替えて求める. 過去の売上は全ての店の行の間で並べ替えるので, 水準の違う店 (30 万円から 120 万円) の値が入り, その効きには店の水準の違いも含まれる

### このタスクで見つけて直したこと

- **推論で重複が残り, 過去の値がずれる (ML-EDA #23)**: 最初は (シード 4 の実験 `2026-11-16/08-31-01` で) 18 のテスト用の期間の誤差が 59,128 円 (8.695 %) で, 学習のときの 59,035 円と合わなかった. 元のデータには重複した行が 150 行あり, 学習では重複を落としてから店ごとに前の行の値をずらすが, 推論の前処理 (`Dataset.transform`) は行を増減する手順を飛ばしていた. そのため重複の後の行の「7 つ前」が 1 日ずれていた. 重複を落としてから推論すると 59,035 円 (8.685 %) になることで原因を確かめ, ML-EDA で, 推論でも行を落とす手順を前後関係のためにかけ, 入力の行の並びに戻すように直した. 目的の列が途中で欠けた履歴も, 学習のときと同じく分かる行だけで前後関係を作るようにした
- **目的の列と特徴量を同じ手順で変えたレシピ (ML-EDA #22)**: `standardize` の `columns` に目的の列と特徴量を並べると, 推論の前処理が手順を丸ごと飛ばし, 特徴量が変換されないまま推論されていた. ML-Inference のレビューで見つけ, 目的の列だけを除いてかけるように直した (17 と 18 のレシピは当てはまらない)
- **結果の画面で決め方の欄が 2 つ出る (ML-Provide #3)**: 画面で出し直したときに見つけた

### 学習のスクリプトの外でしたことを一式に書く必要

17 と 18 は, どちらも学習のスクリプトが前処理の外で入力か目的の値を変えている (17 は並びの先頭に [CLS], 18 は売上の標準化). レシピとモデルの定義だけからは分からないので, 一式を作る人が `prepend` と `target_scale` に書く必要がある. 最初は, 書き忘れても一式を作れてしまい (見本の推論は形しか確かめない), 誤った予測が黙って出た. 17 で `prepend` を書かずに作ると, テスト用の正解率は 0.9445 ではなく 0.8565 になった ([CLS] の無い並びでも位置の埋め込みに収まるので形の誤りにならない). 18 は標準化した値のまま (平均 0 付近) の予測になった.

そこで ML-Inference #3 で, 一式を作るときに検証用の分割を推論し, 実験の記録 (監視した指標のベストの値) と比べるようにした. 正しい一式は上の表のとおり記録と一致し, 書き忘れた一式は記録と合わない注意が出る (17: 正解率 0.8621 と記録 0.9416, 18 のシード 4 の実験: 平均絶対誤差 799,538 円と記録 58,259 円). ML-Provide の一式の画面にも, 合わない場合は上に注意を出す (ML-Provide #4). ただし比べられるのは, 学習のスクリプトが検証用の正解率か元の単位の平均絶対誤差を記録している場合だけ. より確かなのは, 前処理の外でしたことを知っている学習のスクリプトが自分で一式を作ること. 17 と 18 の `train.py` は, 学習の最後に `make_bundle` で実験のディレクトリの中 (`inference/`) に一式を作るようにした (`train.log` に検証用の評価と記録が合うかを残す. 上の 2 つの実験で, どちらも合う). 将来は, 問題の設定の段階が前処理の外の変換を持たないようにするのが良いと考えている
